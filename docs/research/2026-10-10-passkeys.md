# Existing passkey assertion research

Observed: 2026-10-10. This is dated research for M5, not a compatibility claim.
Sources were read without running a real Bitwarden account, a real relying party
or the official extension. Design decisions derived from it are in
[ADR 0007](../adr/0007-existing-passkey-assertions.md).

## WebAuthn Level 3

- `get()` rejects an opaque caller origin with `NotAllowedError` and an effective
  domain that is not a valid domain, including IP addresses, with `SecurityError`.
  An explicit `rpId` must equal the effective domain or be a registrable domain
  suffix of it; otherwise only a client supporting related origin requests may
  continue. Without `rpId`, the effective domain is used.
  [DiscoverFromExternalSource](https://www.w3.org/TR/webauthn-3/#sctn-discover-from-external-source)
- The "registrable domain suffix" test rejects a suffix that is itself a public
  suffix or a suffix of the origin's public suffix. HTML uses the full Public
  Suffix List, including its private section.
  [HTML host suffix](https://html.spec.whatwg.org/multipage/browsers.html#is-a-registrable-domain-suffix-of-or-is-equal-to)
- Client data for `get()` is serialized in a fixed member order: `type`,
  `challenge` (unpadded base64url), `origin`, `crossOrigin`, and `topOrigin` only
  when the caller is cross-origin with its ancestors.
  [Client data serialization](https://www.w3.org/TR/webauthn-3/#clientdatajson-serialization)
- `authenticatorGetAssertion` treats `requireUserPresence` as the constant `true`
  and requires an authorization gesture confirming consent for the selected
  credential. A test of user presence is an interaction with the authenticator;
  it is not user verification. The gesture prompt may be shown by the user agent.
  [authenticatorGetAssertion](https://www.w3.org/TR/webauthn-3/#sctn-op-get-assertion),
  [test of user presence](https://www.w3.org/TR/webauthn-3/#test-of-user-presence)
- A relying party verifies that UP is set. It should require UV only when the
  request asked for `required`; otherwise it ignores UV. BS without BE is
  invalid, and a relying party may compare BE/BS with its stored record. A zero
  signature counter is valid when both the response and stored counter are zero.
  [Verifying an assertion](https://www.w3.org/TR/webauthn-3/#sctn-verifying-assertion)
- Section 16 publishes deterministic ES256 registration and authentication
  vectors for RP ID `example.org`. The authentication vector has flags `0x19`
  (UP, BE, BS), counter zero, a fixed `clientDataJSON` and a DER signature.
  Browser ECDSA signing is randomized, so implementations can compare bytes for
  client data and authenticator data, and verify signatures, but cannot reproduce
  the vector's RFC 6979 signature through WebCrypto.
  [Test vectors](https://www.w3.org/TR/webauthn-3/#sctn-test-vectors)

## Bitwarden behavior at the pinned client revision

Observations come from
[Bitwarden clients `8246ae9`](https://github.com/bitwarden/clients/tree/8246ae9c9a484a0a69f8b27203034555fb872523/libs/common/src/platform/services/fido2),
the same revision used for URI-match semantics.

- Stored credentials use `keyType` `public-key`, `keyAlgorithm` `ECDSA`,
  `keyCurve` `P-256`, a base64url PKCS #8 `keyValue`, a base64url `userHandle`,
  a decimal `counter` string and a `discoverable` string. Credentials it creates
  start with counter zero.
- Credential IDs are either a GUID string representing 16 raw bytes or `b64.`
  followed by base64url bytes for imported credentials.
  [credential-id-utils.ts](https://github.com/bitwarden/clients/blob/8246ae9c9a484a0a69f8b27203034555fb872523/libs/common/src/platform/services/fido2/credential-id-utils.ts)
- Assertions always set BE and BS because vault credentials are synced. They set
  UP after the user picks a credential, or with `assumeUserPresence` after the
  user selects it from Bitwarden's inline menu. UV is set only after a successful
  verification prompt, which is required for `userVerification: "required"` or a
  master-password reprompt item.
- A nonzero counter is incremented and written to the server before signing.
  A zero counter is never incremented or written. Organization ciphers are not
  excluded from assertions.
- Signatures use WebCrypto ECDSA P-256 SHA-256 with conversion from IEEE P1363
  to DER. RP ID hashing uses the ASCII RP ID string.
  [fido2-authenticator.service.ts](https://github.com/bitwarden/clients/blob/8246ae9c9a484a0a69f8b27203034555fb872523/libs/common/src/platform/services/fido2/fido2-authenticator.service.ts)
- Its client builds `clientDataJSON` without `topOrigin`, validates RP IDs with
  tldts (`allowPrivateDomains`), allows `http://localhost`, rejects IPs, and can
  fall back to related origin requests. It returns `FallbackRequested` so the
  page script calls the browser's native implementation, for example when every
  allowed credential lists only non-internal transports.
  [fido2-client.service.ts](https://github.com/bitwarden/clients/blob/8246ae9c9a484a0a69f8b27203034555fb872523/libs/common/src/platform/services/fido2/fido2-client.service.ts),
  [domain-utils.ts](https://github.com/bitwarden/clients/blob/8246ae9c9a484a0a69f8b27203034555fb872523/libs/common/src/platform/services/fido2/domain-utils.ts)
- Its page script wraps `navigator.credentials.get/create`, constructs plain
  objects whose prototypes are changed to `PublicKeyCredential` and
  `AuthenticatorAssertionResponse`, and races conditional requests against the
  native browser request.
  [webauthn-utils.ts](https://github.com/bitwarden/clients/blob/8246ae9c9a484a0a69f8b27203034555fb872523/apps/browser/src/autofill/fido2/utils/webauthn-utils.ts)

## Pinned SDK surface

`@bitwarden/sdk-internal` `0.2.0-main.1034` exposes `decrypt_fido2_credentials`
and `decrypt_fido2_private_key` on the cipher client, which Pateat's local crypto
session already wraps. The WASM declarations expose no FIDO2 authenticator,
assertion or client-data operation. Assertion construction therefore remains
Pateat code over WebCrypto; the SDK supplies decryption only.

## Relying-party verification defaults

Server libraries differ in UV defaults, so UV-clear assertions are not uniformly
accepted even when a site requests `preferred`:
[SimpleWebAuthn `787ca82`](https://github.com/MasterKale/SimpleWebAuthn/blob/787ca8209e39bc5f868a6a42f6b98a1bc1c06206/packages/server/src/authentication/verifyAuthenticationResponse.ts)
defaults `requireUserVerification` to true, while
[py_webauthn `c9ba2b7`](https://github.com/duo-labs/py_webauthn/blob/c9ba2b7dad6b76bec89e44c76c8ed81fc43287bb/webauthn/authentication/verify_authentication_response.py)
defaults `require_user_verification` to false. Both accept a zero counter when the
stored counter is also zero. Site compatibility therefore needs controlled tests;
library defaults are not evidence about any particular site.
